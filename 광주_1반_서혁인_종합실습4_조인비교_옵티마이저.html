프로그램 설명
종합실습4 요구사항 중 "3가지 조인 전략 비교"와 "(Option) DBMS 엔진별 옵티마이저 조사"를 정리한 문서
설명 비고
조인 비교는 추측이 아니라, 실제 ecom_lab4 DB에서 enable_nestloop / enable_hashjoin / enable_mergejoin 옵션으로 플래너에게 강제로 각 조인 전략을 쓰게 한 뒤 EXPLAIN ANALYZE로 실측한 결과를 근거로 작성함
사용 데이터
ecom.orders, ecom.order_items (최근 30일 paid / shipped / delivered 주문, 약 1,898건 주문 · 5,234건 주문상세)
데이터 비고
실측 시각 2026-07-24, 로컬 PostgreSQL 18.4 기준. 데이터 규모가 작아(주문 9,650건) 실행시간 차이는 크지 않지만, Buffers(실제 읽은 페이지 수)로 보면 전략별 차이가 뚜렷하게 드러남
작성자
서혁인 (광주 1반)

1. 테스트에 사용한 공통 쿼리

SELECT o.order_id, oi.line_total
FROM ecom.orders o
JOIN ecom.order_items oi ON oi.order_id = o.order_id
WHERE o.order_status IN ('paid','shipped','delivered')
  AND o.order_ts >= now() - interval '30 days';

동일한 쿼리를 enable_* 옵션으로 조인 전략만 바꿔가며 3번 실행했다.

3. 조인별 차이점 정리

3-1. Nested Loop Join (NLJ)

동작 방식바깥 테이블(driving table)의 각 행마다, 안쪽 테이블에서 조건에 맞는 행을 매번 다시 찾는다. (o.order_id 1,898건 × 개별 인덱스 탐색)
장점안쪽 테이블에 좋은 인덱스가 있고, 바깥 테이블 결과가 적을 때(선택도가 높을 때) 매우 빠르다. 메모리 사용량이 적고 첫 행을 즉시 반환해 LIMIT/스트리밍에 유리하다.
단점바깥 테이블 행 수가 많아지면 반복 횟수(loops)가 그만큼 늘어나 O(N×M)에 가까워진다. 이번 실측에서 Buffers가 가장 높게 나온 이유다.
적합한 상황"고객 1명의 주문 내역 조회"처럼 바깥 결과가 소수(수십~수백 건)인 조회

3-2. Hash Join

동작 방식둘 중 작은(Build) 쪽을 메모리에 해시 테이블로 만들고, 큰(Probe) 쪽을 한 번만 스캔하며 해시로 매칭한다.
장점양쪽 테이블이 크고 인덱스가 마땅치 않아도 O(N+M)에 가깝게 동작한다. 대용량 배치/집계성 쿼리에 강하다. 이번 실측에서 실행시간·Buffers 모두 가장 균형 잡힌 결과를 보였다.
단점Build 쪽 데이터가 work_mem을 초과하면 디스크에 여러 배치로 나눠 써야 해서(Batches > 1) 느려질 수 있다. 등가(=) 조인 조건에서만 사용 가능하다(범위 조인 불가).
적합한 상황오늘 다룬 Q1~Q10처럼 대량의 orders ↔ order_items를 통째로 집계하는 리포트성 쿼리

3-3. Merge Join (Sort-Merge Join)

동작 방식양쪽을 조인 키로 정렬한 뒤, 커서 두 개를 동시에 이동시키며 병합(merge)한다.
장점양쪽이 이미 정렬돼 있거나(인덱스로 정렬 순서 보장) 정렬 비용이 저렴하면 매우 효율적이다. 부등호(<, >, BETWEEN) 조인 조건도 지원한다.
단점어느 한쪽이라도 정렬이 안 되어 있으면 Sort 단계가 추가 비용으로 붙는다. 이번 실측에서 orders 쪽 Sort 때문에 세 전략 중 가장 느렸다.
적합한 상황양쪽 모두 조인 키에 인덱스가 있어 정렬 비용이 거의 없는 경우, 혹은 범위 조인
