2. Materialized View (mv_daily_gmv) 활용

요구사항: 일별 총매출(GMV) 리포트를 mv_daily_gmv로 가속하고, 갱신 전략(오후 3시)을 설계
갱신 전략 — 매일 오후 3시(15:00) 1회 REFRESH CONCURRENTLY
GMV 리포트는 초 단위 최신성이 필요 없는 "일 단위 경영 지표"이므로, 오전 주문/취소/환불이 어느 정도 정리되는 오후 시점에 하루 1회 갱신하는 것으로 설계했다. REFRESH MATERIALIZED VIEW CONCURRENTLY를 사용해 갱신 중에도 리포트 조회가 막히지 않도록 했으며(단, UNIQUE 인덱스 ux_mv_daily_gmv_day 필요), 로컬 PC 환경에는 pg_cron이 기본 설치되어 있지 않아 OS 스케줄러(cron/launchd)에서 매일 15:00에 psql -c "REFRESH MATERIALIZED VIEW CONCURRENTLY ecom.mv_daily_gmv;" 를 실행하도록 등록하는 방식을 제안한다.

3. 3가지 조인 전략 비교 (Nested Loop / Hash Join / Merge Join)

3-1. 테스트에 사용한 공통 쿼리

SELECT o.order_id, oi.line_total
FROM ecom.orders o
JOIN ecom.order_items oi ON oi.order_id = o.order_id
WHERE o.order_status IN ('paid','shipped','delivered')
  AND o.order_ts >= now() - interval '30 days';

동일한 쿼리를 enable_nestloop / enable_hashjoin / enable_mergejoin 옵션으로 조인 전략만 강제로 바꿔가며 3번 실행하여 실측했다.

3-2. 실측 결과 요약

조인 전략Execution TimeBuffers핵심 동작
Hash Join (플래너 기본 선택)7.24 ms368order_items를 해시 테이블로 만들고, orders를 1번 스캔하며 매칭
Nested Loop Join (강제)6.08 ms5,836orders 1,898건 각각에 대해 order_items 인덱스를 1,898번 반복 탐색
Merge Join (강제)9.70 ms421양쪽을 order_id로 정렬 후 병합, orders 쪽 별도 Sort 비용 발생
실행시간은 캐시 효과로 큰 차이가 안 보일 수 있지만, Buffers(버퍼 접근량)는 조인 전략별 부하를 훨씬 정직하게 보여준다. Nested Loop이 시간은 비슷해도 버퍼 접근이 15배 이상 많다.

3-3. 조인별 차이점

Nested Loop Join 바깥 테이블 각 행마다 안쪽 테이블에서 조건에 맞는 행을 매번 다시 찾는다. 안쪽에 좋은 인덱스가 있고 바깥 결과가 적을 때(선택도가 높을 때) 빠르지만, 바깥 행 수가 많아지면 O(N×M)에 가까워진다. "고객 1명의 주문 조회"처럼 결과가 소수인 조회에 적합하다.
Hash Join 작은 쪽(Build)을 메모리 해시 테이블로 만들고, 큰 쪽(Probe)은 한 번만 스캔하며 매칭한다. O(N+M)에 가깝게 동작해 대용량 배치/집계성 쿼리에 강하다. 단, Build 쪽이 work_mem을 초과하면 배치가 나뉘어 느려질 수 있고, 등가(=) 조인에서만 사용 가능하다.
Merge Join 양쪽을 조인 키로 정렬한 뒤 커서 두 개를 이동시키며 병합한다. 이미 정렬돼 있으면 매우 효율적이고 범위(<,>,BETWEEN) 조인도 지원하지만, 정렬이 안 되어 있으면 Sort 비용이 추가된다.
